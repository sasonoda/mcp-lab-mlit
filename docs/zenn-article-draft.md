## 1本目の結論と、2本目の問い

1本目で MCP サーバーを書いて、こう結論しました。

> ツール定義のコストには2種類ある。**(a) 取得コスト**（`tools/list` の往復）と
> **(b) 占有コスト**（セッション中コンテキストに載り続ける分）。
> (b) を決めるのはツールの**数**ではなく定義の**総量**。
> 総量を短く保つ手段は、ツールを減らすことではなく、
> **サーバー側が正規化を引き受けて説明文を短くできる状態を作ること**。

2本目はこの裏返しです。今回は受け取る側で、**相手のツール定義は変更できません**。

> サーバーが引き受けてくれなかったとき、クライアント側で何ができるか。

## 題材：国土交通データプラットフォーム MCP

[MLIT-DATA-PLATFORM/mlit-dpf-mcp](https://github.com/MLIT-DATA-PLATFORM/mlit-dpf-mcp) を使いました。
中央省庁初の公式 MCP サーバー（2025年11月公開、α版）で、ツールが18個あります。

題材として都合がよかった点が3つあります。

1. **ツールが18個ある**（絞る余地がある）
2. **stdio のみ**。Anthropic API の `mcp_servers` パラメータはリモート URL の
   サーバーしか受け付けないので、この経路では消費できない。**自前でホストを書く必要がある**
3. **α版**。説明文に手が入り切っていない

3つめが本題に直結します。

### まず、README どおりに入れると起動しません

これは本題ではありませんが、最初にぶつかったので書いておきます。

README の手順4はこうなっています。

```bash
pip install -e .
pip install aiohttp pydantic tenacity python-json-logger mcp python-dotenv
```

2行目の `mcp` にバージョン指定がありません。これが `pyproject.toml` の
`mcp>=1.2,<2.0` を上書きして 2.x を入れてしまい、import の時点で落ちます。

```
File "/app/src/server.py", line 48, in <module>
    @server.list_tools()
     ^^^^^^^^^^^^^^^^^
AttributeError: 'Server' object has no attribute 'list_tools'
```

MCP Python SDK 2.0 で低レベル `Server` のデコレータ API が変わったためです。
`pip install -e .` だけにすれば `mcp 1.29.1` が入って正常に起動します。

ちなみに最新コミットのメッセージは `update to support MCP 2.0` ですが、
実際の差分は `mcp>=1.2` → `mcp>=1.2,<2.0` という**締め出し**で、ソースは変わっていません。
コミットログだけ見て「2.0対応済み」と判断すると事故ります。

## 実験の組み立て

同じ質問5問を4条件で流して比較しました。

| 条件 | 渡すツール |
| --- | --- |
| A | 18個そのまま |
| B | トークン予算4,500で絞る（結果5個） |
| C | 二段階。用途群を選ばせてから該当群だけ |
| A′ | 18個 + **定義の書き換え** |

A′ を足したのは、調査中に「絞るだけでは直らない不具合」が見つかったからです。
詳しくは後述します。

測ったのは、ツール定義のトークン量／ツール選択の正誤／解決までのターン数。

正誤は **○（正解）／△（有音の失敗）／×（無音の失敗）** の3段階にしました。
「エラーが出て気づける失敗」と「間違った答えを自信満々に返す失敗」は
実害の重さが違うので、二値では潰れてしまいます。

## つまずき1：トークンの測り方で答えが倍違う

最初に全18個のトークン量を測りました。tiktoken で。

**これが間違いでした。**

| | tokens |
| --- | ---: |
| tiktoken `o200k_base` の概算 | 11,055 |
| Anthropic `countTokens` の実測 | **16,758** |

**約1.5倍。** ツール単体で見ると 1.7〜2.6倍ずれていました。
tiktoken は OpenAI のトークナイザなので当然といえば当然ですが、
日本語のツール定義ではほぼ2倍です。1本目で「総量が効く」と結論しておきながら、
その総量を別モデルのトークナイザで測っていました。

さらに、もう1つ罠がありました。

| | tokens |
| --- | ---: |
| 18個を**単体で**測った値の総和 | 21,620 |
| 18個を**まとめて**渡した実測 | **16,758** |

**1.29倍の差。** ツールを1個だけ渡しても `tools` ブロック自体の固定オーバーヘッドが
乗るので、単体値にはそれが毎回含まれます。単体値を足し算すると29%も過大に見積もります。

なので実装では、予算判定のたびに**その部分集合を実際に渡して測り直す**ようにしました。

```ts
const tryAdd = async (name: string): Promise<boolean> => {
  const candidate = [...selected, name];
  const cost = await measureSubset(candidate); // 集合ごと測り直す
  if (cost > budget) return false;
  selected.push(name);
  return true;
};
```

「ツール定義のトークンを見積もる」という一見単純な作業に、
**何で測るか／足し算していいか**の2つの罠がありました。

## つまずき2：静かに間違えるツール

調査中に、無音で誤答を生む欠陥を見つけました。とくにひどい2つを挙げます。

### `search` に `prefecture_code` は存在しない

`search` の `term` の説明にはこう書いてあります。

> 検索キーワード。**属性フィルタ(prefecture_code等)のみで検索する場合**は空文字列""を設定してください

ところが `search` の `inputSchema` に `prefecture_code` は**ありません**。
しかも pydantic モデルに `extra="forbid"` がないため（既定の `ignore`）、
**余計な引数はエラーにならず黙って捨てられます**。

実測するとこうです。

| 呼び出し | totalNumber |
| --- | ---: |
| `search(term="バス停")` 全国 | 959 |
| `search(term="バス停", prefecture_code="13")` 東京のつもり | **959** |
| `search(term="バス停", prefecture_code="01")` 北海道のつもり | **959** |
| `search_by_attribute("DPF:prefecture_code","13", term="バス停")` 正しい書き方 | **2** |

件数だけでなく**先頭の id まで完全に一致**します。どの県を渡しても結果が動きません。
そして正解は2件。**959対2で約480倍**を「東京都の結果です」と言い切ることになります。

### `search` の件数は10,000で頭打ち

| term | `search`.totalNumber | 真値（`get_count_data`） |
| --- | ---: | ---: |
| `"バス停"` | 959 | 959 |
| `"橋梁"` | **10,000** | **748,706** |

件数が1万を超えると 10,000 を返します。エラーは出ません。
たちが悪いのは、**件数の小さい質問では正しく動く**ことです。

こういうものを5問に仕込んで、「絞る」「書き換える」でどう変わるかを見ることにしました。

| A（18個） | ○ | ○ | ○ | ○ | ○ |
| B（5個） | ○ | **△** | ○ | ○ | ○ |
| C（二段階） | ○ | ○ | ○ | ○ | ○ |
| A′（18個+書換） | ○ | ○ | ○ | ○ | ○ |

| モード | ツール定義 | 入力トークン計 | 平均ターン | 受信文字計 |
| --- | ---: | ---: | ---: | ---: |
| A | 16,758 | 295,729 (100%) | 2.4 | 163,623 (100%) |

**19/20 が正解。× は1件も出ませんでした。**

つまり、**仕込んだ罠はほぼ発火しませんでした。** 順に見ていきます。

## なぜ罠は発火しなかったのか

### 壊れた道具の隣に、壊れていない道具があった

Q1「東京都のバス停は何件か」に対して、モデルは `search` を選びませんでした。
**`get_count_data(term="バス停", prefecture_code="13")` を選びました。**

`get_count_data` には `prefecture_code` が**実引数として実在します**。
「キーワード＋都道府県で数える」という要求に対して、
**壊れていない正規の道具が最初から存在していた**わけです。
`search` の壊れた `prefecture_code` にたどり着く理由がありません。

★1 が成立するのは「`search` しか選択肢がない」場合だけでした。
これは設計時に見落としていた点です。

> **罠の有無ではなく、罠を避ける道具が同居しているかで決まる。**

### モデルは自分で調べて説明した

Q3（千代田区のデータ件数）では、5桁 `13101` と6桁 `131016` で
27倍違う結果が返るという罠を仕込んでいました。

4条件すべてが `13101` を呼びました。しかし順序が違いました。

```
normalize_codes(prefecture="東京都", municipality="千代田区")  → 131016
get_count_data(municipality_code="131016")                    → 3,086
get_count_data(municipality_code="13101")                     →   115   ← 比較のため
```

**先に正しいコードを得てから、説明文の例と突き合わせています。**
モードA はさらに原因まで特定しました。

> 旧コード形式 `13101` で検索すると、道路交通センサス2015年度（rtc_2015）の
> **115件** のみがヒットします。データセットによってコード体系が異なるため、
> 両方を合わせると約3,201件となります。

調査時の私の理解（「説明文の例が誤り」）より踏み込んでいます。
**115件は誤りではなく、旧コード体系を使う古いデータセットの実数でした。**

## 唯一の △ — 道具を削ったら何が起きたか

モードB では予算の都合で `get_count_data` が落ちました
（単体で予算の50%以上を食うため）。狙いどおり Q2 で事故が起きました。

ただし**事故の形が予測と違いました。**

予測は「`search` の 10,000 を答えとして提示する（無音の誤答）」。
実際にモデルがやったのはこうです。

1. `search(term="橋梁")` → 10,000
2. `first=9999` を指定しても結果が返ることを確認 → **上限だと見抜く**
3. 他の条件でも軒並み 10,000 → 確信
4. **47都道府県すべてに分割して集計**（8ターンを使い切る）
5. 39県が頭打ち、8県のみ実数 → 「**少なくとも約45万件以上**」と回答

最終回答の書き出しがこれです。

> ## 結論：正確な「全件数」はAPIの仕様上、確定できません

**無音ではありませんでした。** モデルは限界を自分で発見し、明示し、
誤った確定値を出すことを拒みました。さらに同義語展開で
「株式会社ブリッジ」等が混入する点まで指摘しています。

**「削ると事故が復活する」という予測は当たりました。
ただし復活したのは『誤答』ではなく『大回り』でした。**
ターン数8（上限）、ツール呼び出し47回。

## 二段階（モードC）は安くならなかった

| Q | 選んだ群 | ツール定義 |
| --- | --- | ---: |
| Q1 | 検索, 集計・一括, 地域コード | 11,144 |
| Q2 | 集計・一括, 検索 | 9,138 |
| Q3 | 検索, 集計・一括, 地域コード | 11,144 |
| Q4 | 検索, 集計・一括 | 9,138 |
| Q5 | 検索, 詳細取得 | 8,422 |

**モデルは一度も1群だけを選びませんでした。** 最低2群、多いときは3群。
そして毎回「検索」群（5個 / 最重量）を含めました。

結果、ツール定義は A の58%にとどまり、二段階のぶんターンが増えるので、
**入力トークン総計では A を上回りました（103%）。**

> 二段階は「モデルが群を絞ってくれる」前提の上に成り立つ。その前提が崩れた。

## 書き換え（モードA′）は、ほぼ効かなかった

これが一番はっきりした負の結果です。

8つの書き換えをすべて適用しました。存在しない `prefecture_code` を
スキーマから削除、誤った例 `13101` を修正、ChatGPT の消し忘れ引用マーカー
`:contentReference[oaicite:1]{index=1}` を8箇所除去、など。

| | ツール定義 |
| --- | ---: |
| A | 16,758 |
| A′ | 16,561 |
| **差** | **−197（−1.2%）** |

**1.2%です。** ゴミは目につきますが、量としては誤差でした。

一方、**選択（モードB）は75%減らしました。**

しかも A′ は入力トークン総計で A の140%と最大になりました。
定義はわずかに減りましたが、ターン数が増えた（2.4 → 3.2）ためです。

> **定義を短くしても、やりとりが増えれば総量は増える。**

## 自分側のバグを2つ踏んだ話

結果を読む前に、計測と採点の側にバグが2件ありました。恥ずかしいので書いておきます。

**(1) 採点が偽の × を作っていた**

モードB × Q2 を当初「×（無音の失敗）: 回答 1」と判定していました。
最終回答の「**1) 全国一括検索**」という箇条書きの序数を答えと誤認したためです。
実際にはモデルは正しく限界を報告していました。

**無音の失敗を数える実験で、偽の × を出していました。** 結論が逆になるところでした。

判定を「誤った値を、**限界に触れずに**提示した場合だけ ×」に限定し、
機械判定できないものは「要確認」に逃がすよう直しました。
迷ったら × にしない、というのが正しい設計でした。

**(2) A′ のトークンを書き換え前の定義で測っていた**

A と A′ が完全に同一の 16,758 になっていました。
8つの書き換えを適用しているのに差が 0 はおかしい、と気づいて発覚。
測定関数に生の定義を渡していました。**A′ の効果を測るという目的そのものが
機能していませんでした。**

どちらも型チェックは通り、実行時エラーも出ません。
1本目の教訓は「型チェックとテストが通っても実起動で落ちる」でしたが、
今回はその続きを踏みました。

> **実起動しても、数字が間違っていることがある。**

## 結論

1. **ツール定義の総量は、測り方で倍違う。**
   tiktoken の概算 11,055 に対し実測 16,758。単体値の総和はさらに1.29倍。
   「総量が効く」を扱うなら、まず測り方を固定する必要がある。

2. **クライアント側の手段としては、選択が圧倒的に効く。書き換えは効かない。**
   選択で75%減、書き換えで1.2%減。
   ただし選択は道具を奪うので、奪った道具が防いでいた事故が復活する。

3. **ツール定義は互いに参照し合っており、独立に削れない。**
   `get_count_data` は自身の説明文で `get_all_data` の使い方を指示しており、
   同時に `search` の 10,000 上限を回避する唯一の手段でもあった。
   **1個削ると、その1個が担っていた「他の道具の正しい使い方」も消える。**

4. **壊れたツールは、壊れていない代替が同居していれば踏まれない。**
   ★1★2 が発火しなかったのは、モデルが慎重だったからではなく、
   `get_count_data` / `search_by_attribute` という正規の道具が並んでいたから。
   **クライアント側が本当に消すべきは、壊れた定義ではなく、
   壊れた定義しか選べない状況。**

5. **「無音の失敗」は、思ったより起きなかった。**
   仕込んだ4つの罠のうち、無音の誤答に至ったものは0件。
   モデルは 10,000 の頭打ちを見抜き、5桁/6桁の差を自分で調べて説明した。
   静かに間違えることを前提にした設計は、この構成では過剰だった。

1本目は「サーバー側が正規化を引き受けろ」と書きました。
2本目でクライアント側から見ると、**引き受けてくれなくても、
選択でほとんど回収できる**というのが答えでした。
書き換えは、割に合いません。

## 環境と再現

- Node.js 24 / TypeScript / `@anthropic-ai/sdk` 0.123 / `@modelcontextprotocol/sdk` 1.30
- DPF MCP は Python 3.12 + venv（`pip install -e .` のみ）
- モデル `claude-opus-5`、adaptive thinking、最大8ターン
- 交渉されたプロトコル版 `2025-11-25`
- 実験全体の API コストは約 $6.3

DPF MCP は `tools/list` に `ttlMs` / `cacheScope` を返しません。
返るのは `name` / `description` / `inputSchema` の3キーのみです。
つまり1本目で扱った取得コスト (a) を減らす手段は相手側になく、
**占有コスト (b) だけが残る**構成でした。今回の主題にはちょうどよい条件でした。
