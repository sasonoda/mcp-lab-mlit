## 決定0. 実装フェーズの Python 実行環境

### 結論: **ローカルに Python を入れるほうが効率的**

調査フェーズは Docker で正しかった（環境を汚さずに「そもそも動くか」を見たかった）。
実装フェーズは要件が変わる。

### 理由

**1. 2本目の主題そのものがプロセス起動だから**

作るのは `mcp-client.ts` で `StdioClientTransport` を使い、
DPF MCP を**子プロセスとして起動する**ホスト。
Docker を挟むと、起動コマンドがこうなる。

```
python -m src.server
  ↓
docker run --rm -i --env-file .env -v ...:/app -w /app python:3.12 python -m src.server
```

検証したい「stdio で子プロセスを起動する」構造の真ん中に、
コンテナ境界という**実験の対象ではない変数**が入る。
うまくいかなかったとき、MCP の問題か Docker の問題かの切り分けが毎回発生する。

**2. 反復回数が桁違いに増える**

実験は 5問 × 3モード = 15セッション。これを設計調整のたびに回す。

**実測値（2026-09-03、ローカル venv 構築後に計測）:**

| | 起動〜`initialize` 応答 |
| --- | --- |
| ローカル venv | **約1.1秒**（初回のみ約3.0秒） |
| Docker | 上記に `docker run` のコールドスタート 1〜3秒が上乗せ |

差は **2〜3倍**。1回の実験（15セッション）で 15〜45秒 程度。

> 訂正: 当初この欄に「ローカルは 0.2〜0.4秒」と書いたが、それは素の
> インタプリタ起動の値で、このアプリの import グラフ（aiohttp / pydantic / mcp）を
> 含んでいなかった。実測は 1.1秒。**差は10倍ではなく2〜3倍。**
> ただし決定は変わらない。効いているのは下の理由1・3・4のほう。

（計測項目はトークン量・ツール選択・ターン数で、レイテンシは測らない。
なので計測結果が歪むわけではない。効くのは開発の待ち時間のほう）

**3. 記事の再現性**

Zenn 記事を読んだ人が手元で動かすとき、DPF の README は
「venv を作って `python -m src.server`」と書いてある。
こちらが Docker 前提で書くと、公式手順と食い違う説明を余計に書くことになる。
**1本目と同じで、成果物は「動くリポジトリ」。読者が最短で動かせる形が正しい。**

**4. Docker Desktop が既定で停止している**

このマシンでは調査時も停止していて、起動から始めた。
毎セッション「Docker Desktop を上げる」が前置きになる。

**5. `.env` の扱いが素直**

`config.py` は `load_dotenv()` でカレントの `.env` を読む。
ローカルならそのまま動く。Docker だと `--env-file` かマウントを毎回書く。

### Docker 側の利点と、それが効かない理由

| 利点 | 実装フェーズでどうか |
| --- | --- |
| マシンを汚さない | venv を使えばローカルでも汚れは `.venv/` に閉じる |
| 環境が完全再現できる | `mcp<2.0` さえ固定できればよい。requirements で足りる |
| Python 3.12 を選べる | ローカルでも同じ |

**「マシンを汚さない」は venv でほぼ解決する。**
残る footprint は Python 本体だけ。

### 具体的な手順（推奨）

システム全体を汚したくないなら `uv` を使う手もある。
`uv` は Python 本体を `~/.local/share/uv/python` に閉じて管理するので、
システムの PATH に Python を撒かない。

```bash
winget install --id astral-sh.uv --exact
```

```bash
uv python install 3.12
```

そのうえで DPF MCP 側に venv を作る。

```bash
cd <mlit-dpf-mcp のパス> && uv venv --python 3.12 && uv pip install -e .
```

**`pip install -e .` だけにすること。** README 手順4の2行目
（`pip install ... mcp ...`）を実行すると `mcp` 2.x が入って起動しなくなる。
詳細は調査報告 5-1。

普通の Python インストーラでも同じことはできる。

```bash
winget install --id Python.Python.3.12 --exact
```

### 逆に Docker のままにする条件

以下なら Docker 続行でよい。

- マシンに Python を一切増やしたくないという方針が固い
- 実験を回す回数が少なく、待ち時間が気にならない

その場合は `mcp-client.ts` の起動コマンドを設定で差し替えられるようにして、
`docker run` と直 `python` の両方を書けるようにしておくとよい。
（これは v1 のスコープを膨らませない範囲でできる。設定1項目で済む）

## 決定1. モードBを「個数」で切るか「トークン予算」で切るか

### 状況

引き継ぎ資料はモードBを「静的に絞る（5〜6個）」と定義していた。
調査で分かったのは、**18個のトークン量が極端に偏っている**こと。

| | tokens |
| --- | ---: |
| `get_count_data` | 1510 |
| `get_all_data` | 1103 |
| （この2個で全体の 23.6%） | 2613 |
| 全18個 | 11055 |

そのため「6個」という括り方だと、**何を選ぶかで総量が2.5倍ぶれる**。

| モードBの中身（どれも6個） | tokens | モードA比 |
| --- | ---: | ---: |
| 素直に6個（count/all 込み） | 4918 | 44% |
| 素直に6個（count/all 抜き） | 2972 | 27% |
| 重いの優先で6個 | 5454 | 49% |
| 軽いの優先で6個 | 2125 | 19% |

**19% と 49% は別の実験。** 「6個に絞った」という同じラベルで、
削減効果が2.5倍違う結果が出てしまう。

### なぜこれが今回の主題に直結するか

1本目の結論はこうだった。

> 占有コスト (b) を決めるのはツールの数ではなく定義の総量

**モードBを「個数」で定義すると、この結論を自分で踏み外すことになる。**
逆に「トークン予算」で定義すれば、モードBの設計自体が
1本目の結論を2本目で使い直した形になり、連作としての筋が通る。

参考: 安い順に詰めた場合。

| 予算 | 入る個数 | 実際の量 |
| --- | ---: | ---: |
| 2000 tok | 5個 | 1588 |
| 3000 tok | 7個 | 2661 |
| 4000 tok | 9個 | 3761 |

### 選択肢

- **B-a: トークン予算で切る**（推奨）
  「約3000トークン以内で、5問に答えられる組み合わせ」と定義する。
  1本目の結論の再利用になる。ただし「6個」より説明が一手間増える
- **B-b: 個数で切る**
  引き継ぎ資料のまま。単純で記事にしやすいが、上の2.5倍問題を
  「たまたまこう選んだ」で流すことになる
- **B-c: 両方やる**
  6個版と予算版の2つを走らせて差を見る。**スコープが膨らむので非推奨**
  （固定ルール「規模を膨らませない」に触れる）

### 決めること

> モードBの定義を「個数」「トークン予算」のどちらにするか。
> 予算にするなら上限値をいくつにするか

## 決定2. `get_count_data` をモードBに残すか落とすか

### 状況

これは決定1と絡む。**単独では決められない。**

`get_count_data` は18個中で**最も重い**（1510 tok / 19引数）。
トークン予算でも個数でも、削減圧をかけると真っ先に落選候補になる。

ところが、この重い description の中にこういう一文がある。

> パフォーマンス観点から、まず `get_count_data` でボリューム見積り
> → 必要に応じて `get_all_data` で実データ取得が推奨

つまり **「件数だけ知りたいのに `get_all_data` を選んで事故る」という
引き継ぎ資料が狙っていた失敗を、この1510トークンが未然に防いでいる。**

### 何が起きるか

| モードBの中身 | 予想される挙動 |
| --- | ---: |
| `get_count_data` を残す | トークン削減幅は小さい。ツール選択の正答率は保たれる |
| `get_count_data` を落とす | 削減幅は大きい。だが「件数質問」で `get_all_data` を選ぶ事故が復活する |

**モードBの設計次第で、結論が反転する。**
「絞ったら精度が上がった」とも「絞ったら事故が増えた」とも書ける状態にある。

### だからこそ面白い

これは実験の欠陥ではなく、**実験の見どころ**として書ける。

> ツールを削ると、そのツールが持っていた「他のツールの使い方の説明」も一緒に消える。
> ツール定義は独立ではなく、互いに参照し合っている。

この論点は1本目にはなかった。2本目固有の発見として使える。

### 選択肢

- **2-a: 落とす。そして事故を記事のオチにする**（推奨）
  モードBは「削減を優先した現実的な構成」と定義し、
  そこで起きた事故をそのまま結果として書く
- **2-b: 残す**
  モードBは「精度を落とさない範囲で削る」という定義になる。
  削減幅が小さくなり、A との差が出にくい
- **2-c: 落とした版と残した版の両方**
  一番情報量が多いが、モードが4つになる。**スコープ超過で非推奨**

### 決めること

> モードBは「削減優先」か「精度維持優先」か。
> これを決めれば `get_count_data` の去就は自動的に決まる

## 決定3. `tool-gate.ts` の射程

### 状況

引き継ぎ資料での `tool-gate.ts` の役割は「ツールを絞る層」だった。
調査で、**絞るだけでは直らない不具合**が2つ見つかった。

| | 内容 | 実測 |
| --- | --- | --- |
| ★1 | `search` に `prefecture_code` は存在しないが、説明文が存在を匂わせる。渡すと黙って捨てられる | 全国959件が「東京都の結果」として返る。正解は2件 |
| ★2 | 位置検索の `prefecture_code` はスキーマにあるのに実装で捨てられる | 関東の矩形に大阪を指定しても7件のまま |

どちらも**無音**で、LLM 自身は間違いに気づけない。
そして**モードBでもモードCでも直らない**。
`search` を残す限り★1は起きるし、位置検索を残す限り★2は起きる。

### つまり

「サーバーが正規化を引き受けてくれなかったとき、クライアント側で何ができるか」
という2本目の主題に対して、**「ツールを選ぶ」だけでは答えにならない**ことが
実物で示されてしまった。

### 選択肢

- **3-a: 選択のみ（引き継ぎ資料のまま）**
  `tool-gate.ts` は渡すツールを決めるだけ。★1★2は「起きた事故」として観測・記録する。
  スコープが最小。**結論は「クライアント側の選択だけでは限界がある」になる**
- **3-b: 選択 + 定義の書き換え**（推奨）
  ツールを渡す前に inputSchema と description に手を入れる層を足す。
  やることは実質2つだけ。
  - `search` の `term` の説明から `prefecture_code` の記述を消す
  - 位置検索の `prefecture_code` をスキーマから削る

  **どちらも「消す」操作で、追加実装はほぼない。**
  そして「description を短くすると総量が減る」という1本目の結論とも直結する
  （ゴミ掃除がそのままトークン削減になる）
- **3-c: 選択 + 書き換え + 引数の実行時検証**
  LLM が出した引数を実行前に検証して弾く。
  **v1 のスコープを超える。非推奨**（`.env` 一本、CLI 一本という規模を保つ）

### 3-b を推す理由

- 実装コストが小さい（消すだけ。新しい概念を持ち込まない）
- 主題への答えが「選ぶ」から「書き換える」に一段深くなる
- 5-2 で見つけた ChatGPT の引用マーカー8箇所の除去も同じ層で処理でき、
  「定義の総量を減らす」という1本目の結論の実演になる
- モードを増やさないので規模が膨らまない

ただし**実験設計への影響**がある。
3-b にすると、モードA（18個そのまま）との比較で
「絞ったから良くなった」のか「書き換えたから良くなった」のかが混ざる。
モードの定義に「書き換えあり/なし」をどう織り込むかを、決定1と一緒に決める必要がある。

### 決めること

> `tool-gate.ts` は「選ぶだけ」か「書き換えまでやるか」。
> 書き換えるなら、その効果をモードA/B/C のどこで切り分けるか

## 3つの決定の依存関係

独立ではない。この順で決めるのが早い。

```
決定3（tool-gate の射程）
   ↓ 「書き換えあり/なし」がモード定義の軸を1本増やすか決まる
決定1（モードBの切り方）
   ↓ 「削減優先か精度維持か」が決まる
決定2（get_count_data の去就）
   ↓ 自動的に決まる
```

**決定2は実質、決定1の系。** 独立に悩む必要はない。

## 推奨の組み合わせ（一案）

- 決定3 → **3-b**（選択 + 定義の書き換え。ただし書き換えは全モード共通の前処理とし、モードの軸を増やさない）
- 決定1 → **B-a**（トークン予算 3000 で切る）
- 決定2 → **2-a**（`get_count_data` は落とす。事故をオチにする）

この組み合わせなら、モードは3つのまま、実装は CLI 1本のまま、
そして結論が「ツールの数ではなく定義の総量」（1本目）から
「クライアント側は選ぶだけでなく書き換えられる」（2本目）へ素直に接続する。

**ただしこれは案であって、決定ではない。**
