## 5-1. DPF MCP は起動するか → **条件付きで起動する**

### 実行環境

このマシンに Python が入っていなかったため（Microsoft Store のエイリアスのみ）、
`python:3.12` コンテナ上で検証した。stdio 子プロセス起動という条件は同じ。

```
python 3.12.14 / pydantic 2.13.5 / mcp 1.29.1
```

### 結果A: README どおりに入れると壊れる

README 手順4はこう書いてある。

```bash
pip install -e .
pip install aiohttp pydantic tenacity python-json-logger mcp python-dotenv
```

2行目の `mcp` にバージョン指定がない。これが `pyproject.toml` の `mcp>=1.2,<2.0` を
**上書きして 2.x を入れてしまう**。結果、import の時点で落ちる。

```
File "/app/src/server.py", line 48, in <module>
    @server.list_tools()
     ^^^^^^^^^^^^^^^^^
AttributeError: 'Server' object has no attribute 'list_tools'
```

MCP Python SDK 2.0 で低レベル `Server` の `@server.list_tools()` デコレータ API が
なくなっている。`src/server.py` は 1.x の API で書かれたまま、一行も直っていない。

### 結果B: `<2.0` を守れば起動する

```bash
pip install "mcp>=1.2,<2.0" aiohttp pydantic tenacity python-json-logger python-dotenv
python -m src.server
```

→ `mcp 1.29.1` が入り、正常起動。`initialize` / `tools/list` / `tools/call` すべて応答。
stderr へのログ汚染もなし（`utils.py` の `StreamHandler` は stderr 既定なので stdio を壊さない）。

### 「MCP 2.0 対応」コミットの中身

最新コミット `6ff7f10` のメッセージは `update to support MCP 2.0` だが、実際の差分は2行だけ。

```diff
-  "mcp>=1.2",                 # SDK MCP (server)
+  "mcp>=1.2,<2.0",            # SDK MCP (server)
```

（もう1行は問い合わせフォームの URL 差し替え）

**対応ではなく、2.0 を締め出す固定。** ソースコードは 2025-11-04 から変わっていない。
メッセージが実態と逆なので、コミットログだけ見て「2.0対応済み」と判断すると事故る。

### 結論

**起動する。お題の見直しは不要。** ただし依存を自分で固定する必要がある。
`mcp-lab-mlit` 側では README の2行目を使わず、`pip install -e .` だけにするか、
`mcp<2.0` を明示する。この落とし穴自体が記事のネタになる。

## 5-3. プロトコルの版 → **サーバーは版を持っていない**

`initialize` を3つの版で投げて挙動を確認した。

| 送った `protocolVersion` | 返ってきた `protocolVersion` |
| --- | --- |
| `2026-07-28` | **`2025-11-25`**（SDK の上限まで切り下げ） |
| `2025-06-18` | `2025-06-18`（そのまま反響） |
| `2024-11-05` | `2024-11-05`（そのまま反響） |

`src/server.py` は `InitializationOptions(server_name, server_version, capabilities)` を
渡すだけで、**protocolVersion をどこにも書いていない**。版の決定は完全に SDK 任せ。

つまり:

- **DPF が話す版は「リポジトリの内容」ではなく「pip install した日の SDK バージョン」で決まる**
- 今日入れると `mcp 1.29.1` → 上限 `2025-11-25`
- `<2.0` の壁があるので、**`2026-07-28` には到達できない**

### `ttlMs` / `cacheScope`

**存在しない。** `tools/list` のレスポンスは以下だけ。

```json
{ "tools": [ { "name": "...", "description": "...", "inputSchema": {} } ] }
```

- 全18ツールとも **`name` / `description` / `inputSchema` の3キーのみ**
- `ttlMs`, `cacheScope`, `annotations`, `outputSchema`, `title`, `nextCursor` — **すべてなし**

1本目で扱った 2026-07-28 の `ttlMs` / `cacheScope` は、そもそも交渉の土俵に乗らない。
**取得コスト (a) を減らす手段が相手側にない状態で、占有コスト (b) だけが残る。**
2本目の主題（サーバーが引き受けてくれなかったとき何ができるか）に、ちょうど嵌まる条件。

### `Mcp-Session-Id`

使わない。stdio トランスポートなので HTTP ヘッダは存在しない。
セッションは子プロセスの生存期間そのもの。

### capabilities

```json
{"experimental":{}, "tools":{"listChanged":false}}
```

`resources/list` と `prompts/list` は両方 `-32601 Method not found`。
**ツールだけのサーバー。** クライアント実装で resources/prompts を考えなくてよい。

### クライアント実装への帰結

- 版は交渉で下がる前提にする。`2026-07-28` を要求して `2025-11-25` が返る挙動に耐えること
- `ttlMs` / `cacheScope` は来ない前提で書く（新仕様に合わせても得がない）
- **新旧どちらに合わせるかという問いは、実質「旧に合わせるしかない」で決着している**

## 5-4. 取り違えそうなツール

description を実際に読んだ結果。**引き継ぎ資料の見立て3組はすべて当たり。**
加えて、それより深刻な組を見つけた。

### ★最重要（新発見）: `search` に `prefecture_code` は存在しない

これが今回いちばんの収穫。

`search` の `term` の説明にはこう書いてある。

> 検索キーワード。**属性フィルタ(prefecture_code等)のみで検索する場合**は空文字列""を設定してください

ところが `search` の `inputSchema` に `prefecture_code` は **ない**。
引数は `term / first / size / sort_attribute_name / sort_order / phrase_match / minimal` の7つだけ。

さらに、pydantic モデルに `extra="forbid"` が設定されていないため（既定の `ignore`）、
**余計な引数はエラーにならず黙って捨てられる**。実測:

```python
SearchBase(**{"term":"バス停","prefecture_code":"13"})
# -> {'term': 'バス停', 'first': 0, 'size': 50, ...}   prefecture_code は消滅
```

つまり「東京都のバス停を検索して」に対して LLM が

```
search(term="バス停", prefecture_code="13")
```

と呼ぶと、**エラーも警告も出ないまま全国検索の結果が返る。**
LLM はそれを「東京都の結果」として要約する。**静かに間違える。**

#### 実データで確認済み（2026-09-03 追記・APIキー取得後）

| 呼び出し | totalNumber |
| --- | ---: |
| A. `search(term="バス停")` — 全国 | **959** |
| B. `search(term="バス停", prefecture_code="13")` — 東京のつもり | **959** |
| D. `search(term="バス停", prefecture_code="01")` — 北海道のつもり | **959** |
| C. `search_by_attribute("DPF:prefecture_code","13", term="バス停")` — 正しい書き方 | **2** |

A / B / D は totalNumber だけでなく**先頭の id まで完全に一致**した。
どの都道府県コードを渡しても結果が動かない。捨てられている証明になっている。

そして正解は **2件**。**959 対 2 で、約480倍を「東京都の結果です」と言い切る**ことになる。
桁が違うので、LLM 自身も出力を見て異常に気づけない。実験の目玉はここで確定。

しかも `server.py` の `validate_and_provide_hints()` は、この間違いを助長する側に働く。
`prefecture_code` を term なしで渡すと「term を付けろ」というヒントを返すので、
LLM は `term=""` を足して再送し、**やはり prefecture_code は捨てられる**。
ヒント層が silent failure の経路へ誘導している。

正しい呼び方は `search_by_attribute(attribute_name="DPF:prefecture_code", attribute_value="13", term="バス停")`。

### ★2番目: 位置検索の `prefecture_code` は受け取るが使われない

`search_by_location_rectangle` / `search_by_location_point_distance` には
`prefecture_code` が **スキーマに存在する**。説明も積極的だ。

> 都道府県コード (例: '13'=東京都)。normalize_codesツールで正規化できます。**位置検索と組み合わせて結果を絞り込めます**

`SearchByRect` にもフィールドがあり、`p.prefecture_code` としてパースまでされる。
しかしその後の呼び出しは:

```python
data = await client.search_by_rectangle(
    p.rectangle.top_left_lat, ..., term=p.term or "", first=..., size=..., phrase_match=...)
    # prefecture_code は渡されない
```

`client.search_by_rectangle()` の引数にも存在しない。**受け取って、検証して、捨てている。**
`search` のケースと違いスキーマに載っているぶん、LLM は堂々と使う。こちらのほうが踏みやすい。

#### 実データで確認済み（2026-09-03 追記）

関東を覆う矩形（35.2–36.2N / 138.9–140.3E）に `term="バス停"` で固定し、
`prefecture_code` だけ変えた。

| 呼び出し | totalNumber |
| --- | ---: |
| E1. 矩形のみ（基準） | **7** |
| E2. 矩形 + `prefecture_code="27"`（大阪） | **7** |
| E3. 矩形 + `prefecture_code="13"`（東京） | **7** |

**関東の矩形に大阪を指定しても件数が変わらない。** 完全に無視されている。

### ★3番目: 「位置だけで検索可能か」でツール間の記述が矛盾

| ツール | 記述 |
| --- | --- |
| `search_by_location_rectangle` | term は「**位置のみで検索する場合は省略可能**」 |
| `search_by_location_point_distance` | 同上 |
| `get_all_data` | 「`locationFilter`（矩形など）**単独では検索不可**です。必ず `term` または `attributeFilter` を併用してください」 |
| `get_count_data` | 「公式仕様上、`locationFilter`（空間条件）**のみでは検索不可**」 |

同じ API 制約について、正反対のことを言っている。
LLM は自分が選んだツールの説明しか強く見ないので、
`search_by_location_rectangle` を term なしで呼んで失敗する筋がある。

### 引き継ぎ資料が挙げた3組の検証

#### (1) `search` vs `search_by_attribute` → **紛らわしい。ただし理由は想定と違う**

境界線自体は description に明記されている（`search` の注意書きが
「メタデータ検索は search_by_attribute を使え」と誘導している）。文面だけ見れば分けられる。

問題は上の★1で、**`search` の引数説明が `prefecture_code` の存在を匂わせている** こと。
「境界が曖昧」ではなく「境界を跨げると誤解させる記述がある」。質問設計はここを突くべき。

#### (2) `get_data` / `get_all_data` / `get_count_data` → **想定どおり事故る。ただし本命は別**

- `get_data` は `dataset_id` + `data_id` **必須**。ID を知らない段階では呼べない。
  「詳細が欲しい」だけでは選べないので、実は誤選択しにくい
- `get_all_data` と `get_count_data` は **両方とも required なし**。
  引数ゼロでも呼べてしまう。ここが危ない
- `get_count_data` の説明には親切な誘導が入っている:

  > パフォーマンス観点から、まず `get_count_data` でボリューム見積り → 必要に応じて `get_all_data` で実データ取得が推奨

  これは効くはずだが、`get_count_data` は **19引数 / 1510 tokens で18個中最重量**。
  モードBでこれを落とすと、その瞬間に「件数だけ知りたいのに `get_all_data`」の事故が復活する。
  **モードBの設計次第で結果が反転する、実験として一番おいしい箇所。**
- **より紛らわしい実の組は `get_data` vs `get_data_summary`。**
  required が完全に同一（`dataset_id`, `data_id`）、用途の差は「詳細 or タイトルだけ」のみ。
  引数から区別できず、description の一行しか手がかりがない。同じ構図が
  `get_data_catalog` vs `get_data_catalog_summary` にもある（こちらは required なし同士）

#### (3) ダウンロード URL 系3つ → **想定と違い、区別は容易**

`get_file_download_urls` / `get_zipfile_download_url` / `get_thumbnail_urls` は
用途が「個別ファイル / ZIP 一括 / サムネイル画像」と明確に分かれている。
3つとも `(A) files 配列を直接渡す` / `(B) dataset_id + data_id を渡す` の同じ二択構造で、
説明の書式も揃っている。**ここは誤選択しにくい。** 質問5問の枠を使うのは惜しい。

ただし別の問題がある。3つとも **required が空** で、
`files` も `dataset_id` も渡さずに呼べてしまう。二択のどちらも満たさない呼び出しが素通りする。

### ★おまけ: `normalize_codes` 周辺の三つ巴と桁数の矛盾

`get_prefecture_data` / `get_municipality_data` / `normalize_codes` は用途が重なる。
「東京都のコードは？」に対して3つとも正解になりうる。
`normalize_codes` の説明は明示的に先行実行を促している。

> このツールを他の検索ツールの前に実行することで、正確なprefecture_code/municipality_codeを取得できます

さらに市区町村コードの桁数が食い違っている。

| 出典 | 記述 |
| --- | --- |
| `normalize_codes` | 「市区町村名から **5桁** コードを取得」 |
| `search_by_attribute` | `municipality_code: '13101' (千代田区)` → 5桁 |
| `get_municipality_data` | 「アプリ側で扱いやすいのは **6桁の文字列** `code_as_string`（例: **"13101"**）」 |

`get_municipality_data` の記述は **それ自体で矛盾している**（"13101" は5桁）。

### 質問5問の材料としての優先順位

事故の「静かさ」で並べると、実験の見どころは次の順になる。

1. **`search` + `prefecture_code`** — 引数が黙って消え、間違った答えが自信満々に返る（無音・最悪）
2. **位置検索 + `prefecture_code`** — スキーマ公認なのに無視される（無音）
3. **`get_count_data` vs `get_all_data`** — 件数だけ欲しいのに全件取得（有音・重い）
4. **`get_data` vs `get_data_summary`** — required 同一で区別不能（軽微）
5. **`normalize_codes` を先に呼ぶか** — 二段階を踏めるかの試験

1と2は「ツール定義を絞る」だけでは直らない。**クライアント側が引数を検証して弾く** か、
**そもそも壊れた引数を持つツールを渡さない** しかない。
2本目の主題「サーバーが引き受けてくれなかったとき、クライアント側で何ができるか」に
そのまま刺さる素材になっている。`tool-gate.ts` の役割が
「ツールを絞る層」から「ツール定義を書き換える層」に広がる可能性がある。

## 6. 未確認事項 → **解消済み（2026-09-03 追記）**

APIキーを取得したため、保留していた実データ確認をすべて実施した。結果は上記
★1（959 対 2）★2（関東矩形に大阪を指定しても7件のまま）に反映済み。
**調査フェーズに未確認事項は残っていない。**

残る環境上の論点はひとつだけ。

- このマシンには Python が入っていない。調査はコンテナで代用した。
  実装フェーズの実行環境をどちらにするかは別途判断（`docs/open-decisions.md` 参照）

### 鍵の取り扱い

- `docs/key.txt` に置かれていたキーを `.env`（リポジトリ直下）へ移した
- `.gitignore` を作成し、`.env` と **`docs/key.txt` の両方**を除外した
- `.env.example` を用意した
- **`docs/key.txt` は役目を終えたので削除を推奨。**
  `docs/` は公開リポジトリに入るディレクトリなので、
  ガードレール「APIキーはリポジトリにコミットしない」に直接触れる位置にある
