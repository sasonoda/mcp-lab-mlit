## 0. 推奨からの変更点（1点だけ）

`open-decisions.md` では「書き換えは全モード共通の前処理とし、モードの軸を増やさない」と書いた。
**設計に落とす段階でこれは成立しないと分かったので、1点だけ変えている。**

全モードに書き換えを適用すると、★1★2（無音の事故）が**どのモードでも起きなくなる**。
事故が消えるので、書き換えの効果が測れない。書くコードの効果を測れないのは本末転倒。

そこで **書き換えなしを既定とし、書き換え版を A′ という1条件として測る** 形にした。

- 主グリッドは予定どおり **A / B / C の3モード**
- そこに **A′ = A + 書き換え** を足す（合計4条件 × 5問 = 20セッション）
- 追加コストは設定フラグ1つと自動実行5回分のみ。**新しいコードは増えない**
  （書き換えの実装は決定3-b で元々必要）

これ以外は推奨どおり。

## 1. 調査の追補（設計中に判明した事実）

質問の正解を確定させるため実データを引いたところ、調査報告になかった欠陥が3つ出た。
いずれも**無音**で、質問設計に直接使う。

### 追補1: `search` の `totalNumber` は 10000 で頭打ち

| term | `search`.totalNumber | `get_count_data` の真値 |
| --- | ---: | ---: |
| `"バス停"` | 959 | 959 |
| `"橋梁"` | **10000** | **748,706** |
| `"道路"` | **10000** | （同様に頭打ち） |
| `""` | **10000** | 3,227,279 |

**件数が1万を超えると `search` は 10000 を返す。** エラーは出ない。
「橋梁は10000件です」と答えると、真値 748,706 に対して**74分の1**。

たちが悪いのは、**件数の小さい質問では正しく動く**こと（バス停は959で一致）。
小さい例で「`search` の totalNumber で件数が取れる」と学習すると、大きい質問で必ず外す。

### 追補2: 市区町村コードは5桁と6桁で別物。どちらもエラーにならない

`normalize_codes(prefecture="東京都", municipality="千代田区")` が返すのは **`131016`（6桁）**。

| `DPF:municipality_code` に渡す値 | totalNumber |
| --- | ---: |
| `"13101"`（5桁。**ツール説明の例そのまま**） | **115** |
| `"131016"`（6桁。normalize_codes の出力） | **3086** |

**27倍違う結果が、どちらもエラーなしで返る。**
`search_by_attribute` の説明にはこう書いてある。

> - municipality_code: '13101' (千代田区)

**ツール自身の例が誤り。** 例に従うと 3086 件中 115 件しか見ずに答えることになる。

調査報告 5-4 で「5桁と6桁の記述が食い違う」と指摘した箇所は、
単なる誤記ではなく**実際に結果が変わる**ことが確定した。

### 追補3: `normalize_codes` は市区町村名だけでは動かない

`normalize_codes(municipality="千代田区")` → 全フィールド `null`。

```json
{"prefecture_code": null, "municipality_code": null, "candidates": [],
 "warnings": ["municipality_without_prefecture: provide prefecture for disambiguation"]}
```

説明の使用ケース2はこう書いてある。

> 2. 市区町村名から5桁コードを取得

**単独では取得できない。** `prefecture` の同時指定が必要。
これは warnings が出るので**有音の失敗**。回復可能。

### 追補4: `cals_construction` は存在しない

4つのツール説明が例として使っている `dataset_id="cals_construction"` は、
`search_by_attribute` で引くと **totalNumber = 0**。
実在する dataset_id は `nlni_ksj-p14` など（`get_count_data` の `slice_type="dataset"` で列挙できる）。

### 追補5: ★3の矛盾は「位置検索は単独で可能」で決着

調査報告 5-4 ★3 で、位置のみの検索が可能かツール間で記述が矛盾していた。実測した。

`search_by_location_point_distance(lat, lon, distance)` は
`term` を省略しても `term=""` でも **668件** を返す。**単独で検索できる。**

「locationFilter 単独では検索不可」は `get_all_data` / `get_count_data` にのみ当てはまる制約で、
`search_by_location_*` には当てはまらない。**location 系の説明のほうが正しい。**

## 2. モード定義

### 共通条件

- モデル: `claude-opus-5`
- MCP サーバー: DPF MCP を stdio で子プロセス起動（ローカル venv）
- 各セッションは独立。会話履歴を跨がない
- 1問あたりの最大ターン数: **8**（超えたら打ち切り、未解決として記録）
- `tool-gate.ts` が全モードのツール供給口。モードは gate の設定で切り替える

### モードA — 18個そのまま（基準）

`tools/list` の結果を無加工で渡す。

- ツール数 18 / **16,758 tokens**（countTokens 実測。当初書いた 11,055 は tiktoken の概算で約1.5倍の誤り）
- ★1★2および追補1〜4の罠がすべて有効

### モードB — トークン予算（確定 4500）

**選定ルール（先に固定し、結果を見てから動かさない）:**

1. 上限 4,500 tokens（当初 3,000。再校正の経緯は下の「実測後の確定値」）
2. 用途群5つ（検索 / 詳細取得 / 集計・一括 / ダウンロード / 地域コード）を、
   **安いものから順にカバーする**
3. 同じ群に複数あるときは安いほうを採る
4. 予算を超えるものは、群ごと落とす

**選定は実装（`src/tool-gate.ts` の `selectForModeB`）が実行時に計算する。**
ルール2の「必要な能力」は次の5つで、能力ごとに最も安いツールを採る。

| 能力 | 候補 |
| --- | --- |
| keyword-search | `search` |
| attribute-search | `search_by_attribute` |
| location-search | `search_by_location_point_distance` / `search_by_location_rectangle` |
| detail-summary | `get_data_summary` / `get_data` |
| region-normalize | `normalize_codes` |

### 実測後の確定値（2026-09-03）

**予算は 3,000 → 4,500 に再校正した。**

当初の 3,000 は tiktoken の概算合計 11,055 に対する約27%として置いた値だった。
`countTokens` の実測では全18個が **16,758**（概算の約1.5倍）あり、
3,000 のままだと **3個しか入らず Q3・Q4 が回答不能**になる
（`normalize_codes` と位置検索が落ちるため、そもそも道具がない）。

同じ割合（27.1%）を実測に当てはめると 4,541。丸めて **4,500** とした。

| 予算 | 個数 | 実測 | 5能力カバー |
| ---: | ---: | ---: | --- |
| 3,000 | 3 | 2,908 | 3/5 ← Q3・Q4 が回答不能 |
| 4,000 | 4 | 3,713 | 4/5 ← Q3 が回答不能 |
| **4,500** | **5** | **4,206** | **5/5** |
| 5,000 | 6 | 4,615 | 5/5 |

確定した選定（`selectForModeB` が実行時に計算した結果）:

| ツール | 集合に足した時点の実測累計 |
| --- | ---: |
| `search` | 1,239 |
| `search_by_attribute` | 2,406 |
| `search_by_location_point_distance` | 3,211 |
| `get_data_summary` | 3,713 |
| `normalize_codes` | **4,206** |

**5個 / 4,206 tokens（モードA比 25%）。**

**`get_count_data` は落ちた**（足すと 6,470 で予算超過）。`get_all_data` も落ちた（5,811）。
予算を 3,000 にしても 4,500 にしても集計群は落ちる。
恣意的な選別ではなくルールの帰結であり、それ自体が観測対象（決定2）。

`get_count_data` は単体で予算の **50%** を食う。ルール2「安いものから」に素直に従うと、
集計群は丸ごと落ちる。**恣意的に落としたのではなく、予算ルールの帰結。**
ここが決定2で言っていた「削ると事故が復活する」の実装。

### モードC — 二段階

ターン1で用途群だけを提示し、選ばせてから該当群のツールを渡す。

セレクタは擬似ツール1個（約 **150 tokens**）。

| 群 | 個数 | tokens |
| --- | ---: | ---: |
| 検索 | 5 | 3,249 |
| 詳細取得 | 5 | 2,109 |
| 集計・一括 | 2 | 2,613 |
| ダウンロード | 3 | 1,675 |
| 地域コード | 3 | 1,409 |

1問あたりの実コストは `150 + 選ばれた群` の合計（複数群を跨ぐ質問では加算）。
**質問によってはモードAより高くつく可能性がある。** それも結果として記録する。

### モードA′ — 18個 + 定義の書き換え

モードAと同じ18個を渡すが、`tool-gate.ts` が渡す前に定義を書き換える。
**やるのは「消す」操作だけ。追加しない。**

| # | 対象 | 操作 | 根拠 |
| --- | --- | --- | --- |
| 1 | `search` の `term` の説明 | 「属性フィルタ(prefecture_code等)のみで検索する場合は」を削除 | ★1。存在しない引数を匂わせている |
| 2 | `search_by_location_rectangle` / `..._point_distance` | `prefecture_code` を inputSchema から削除 | ★2。受け取るが使われない |
| 3 | `search_by_attribute` の説明 | 例 `'13101' (千代田区)` を `'131016'` に修正 | 追補2。例が誤りで27倍ずれる |
| 4 | `normalize_codes` の説明 | 「市区町村名から5桁コードを取得」→ 都道府県の同時指定が必要と明記、6桁に訂正 | 追補2・3 |
| 5 | `search` の `size` の説明 | totalNumber が10000で頭打ちになる旨を追記（**唯一の追記**） | 追補1。削除では表現できない |
| 6 | 全ツール | `:contentReference[oaicite:N]{index=N}` を除去（8箇所） | 5-2。純粋なゴミトークン |
| 7 | 全ツール | 例示 `cals_construction` を実在IDに差し替え | 追補4 |

書き換え後のトークン量は実装時に実測して記録する（**減ることを期待するが、5だけ増える**）。

## 3. 質問5問と正解列

すべて実データで正解を確認済み（2026-09-03）。

### Q1. 「東京都のバス停のデータは何件ありますか？」

- **正解列:** `search_by_attribute(attribute_name="DPF:prefecture_code", attribute_value="13", term="バス停")`
- **正解値:** **2**
- **無音の罠:** `search(term="バス停", prefecture_code="13")` → **959**（全国。約480倍）
- 狙い: ★1。存在しない引数が黙って捨てられる

### Q2. 「橋梁のデータは全国で何件ありますか？データそのものは要りません」

- **正解列:** `get_count_data(term="橋梁")`
- **正解値:** **748,706**
- **無音の罠:** `search(term="橋梁", size=1)` の totalNumber → **10,000**（頭打ち。約74分の1）
- **有音の罠:** `get_all_data(term="橋梁")` → 大量取得。ターン数とレスポンス量が爆発
- 狙い: 追補1 + 決定2。**モードBには `get_count_data` がないので、必ずどちらかの罠に落ちる**

### Q3. 「千代田区にあるデータを検索してください」

- **正解列:** `normalize_codes(prefecture="東京都", municipality="千代田区")` → `131016`
  → `search_by_attribute(attribute_name="DPF:municipality_code", attribute_value="131016", term="")`
- **正解値:** **3,086**
- **無音の罠:** 説明の例に従って `"13101"` を使う → **115**（27分の1）
- **有音の罠:** `normalize_codes(municipality="千代田区")` 単独 → null + warnings（回復可能）
- 狙い: 追補2・3。二段階を踏めるか、かつ**踏んだ結果を正しく使えるか**

### Q4. 「東京駅から半径500m以内にあるデータを教えてください」

- **正解列:** `search_by_location_point_distance(location_lat=35.681236, location_lon=139.767125, location_distance=500)`
- **正解値:** **668**
- **無音の罠:** `prefecture_code="13"` を併せて渡す → 無視される（★2）
- **判断の罠:** 他ツールの「位置単独では検索不可」を読んで `term` を足す/諦める（★3）
- 狙い: ★2★3。モードA′では `prefecture_code` がスキーマから消えている

### Q5. 「データセット `nlni_ksj-p14` の中のデータを1件、タイトルだけ知りたい」

- **正解列:** `search_by_attribute(attribute_name="DPF:dataset_id", attribute_value="nlni_ksj-p14", term="", size=1, minimal=True)`
  → `get_data_summary(dataset_id="nlni_ksj-p14", data_id=<取得したid>)`
- **正解値:** タイトル文字列（レスポンス **約114文字**）
- **罠:** `get_data` を選ぶ → **約1,377文字**（12倍。答えは合うが無駄）
- 狙い: `get_data` vs `get_data_summary`。required が同一で引数から区別できない組

### 質問の配分

| 質問 | 主な狙い | モードBで何が起きるはず |
| --- | --- | --- |
| Q1 | ★1 無音・引数消滅 | 変わらず起きる（`search` は残っている） |
| Q2 | 追補1 + 決定2 | **`get_count_data` がないので悪化する** |
| Q3 | 追補2 無音・27倍 | 変わらず起きる |
| Q4 | ★2★3 | `search_by_location_point_distance` は残存 |

Q2 が悪化し Q5 が改善する。**「絞ると良くなる/悪くなる」が同じモードの中で同時に起きる**設計。

## 4. 採点基準

### 4-1. ツール定義のトークン量

- モードごとに、**実際に API に送ったツール定義の合計トークン数**を記録
- モードCは質問ごとに変わるので、質問ごとに記録して平均も出す

**計測方法（実装時に変更。tiktoken は使わない）**

当初この欄には「tiktoken を補助として併記」と書いたが、**tiktoken は使わないことにした。**
OpenAI のトークナイザなので Claude では 15〜20% ずれ、日本語ではさらに大きくずれる。
調査報告 §5-2 の **11,055 はこの概算値**であり、実測とは一致しない。

代わりに Anthropic の **`countTokens` API** で測る。

```
ツール定義のトークン量 = countTokens(messages, tools) − countTokens(messages)
```

- `npm run tools -- --measure` で全18個を1個ずつ測り、`experiments/tool-costs.json` に保存
- **モードB の予算判定はこの実測値を使う**（概算値で予算を切ると選定がずれる）
- 実行時の総量は各リクエストの `usage.input_tokens` でも記録し、突き合わせる

### 実測して分かったこと（2026-09-03）

**1. tiktoken は約半分しか数えていなかった**

| | tokens |
| --- | ---: |
| tiktoken `o200k_base` の概算（調査報告 §5-2） | 11,055 |
| `countTokens` の実測 | **16,758** |

ツール単体で見ると **1.7〜2.6倍**。説明文が短いツールほどずれが大きい
（`get_data_catalog_summary` は 269 → 695 で 2.58倍）。
スキルの警告は「英語以外ではさらに大きくずれる」だったが、日本語のツール定義では
**ほぼ2倍**だった。1本目の「総量」の議論を概算値でやると桁を見誤る。

**2. 単体値を足し算してはいけない**

| | tokens |
| --- | ---: |
| 18個を単体で測った値の総和 | 21,620 |
| 18個をまとめて渡した実測 | **16,758** |

差は 4,862（**1.29倍**）。ツールを1個だけ渡しても `tools` ブロック自体の
固定オーバーヘッドが乗るため、単体値には毎回それが含まれる。

したがって:

- `perTool`（単体値）は**順位付けにだけ使う**
- **予算判定は、その部分集合を実際に渡して測り直す**（`measureSubset`）
- 実装でも `selectForModeB` は候補を1つ足すたびに集合を測り直している

この2点は、それ自体が記事の材料になる。
「ツール定義のトークンを見積もる」という一見単純な作業に、
**測り方の罠が2つある**（何で測るか / 足し算していいか）。

### 4-2. ツール選択の正誤 — **3段階で採点する**

従来の「正解/不正解」の二値では、今回の主眼である**無音の失敗**が表現できない。
「間違った答えを自信満々に返す」と「エラーが出て気づける」は、実害の重さが違う。

| 段階 | 定義 | 記号 |
| --- | --- | --- |
| **正解** | 正解列と一致。最終回答の数値も一致 | ○ |
| **有音の失敗** | 誤ったツール/引数だが、エラーか警告が返り、モデルが気づいて回復できた（または回復できずとも失敗が可視） | △ |
| **無音の失敗** | エラーが出ず、**間違った値を正しいものとして最終回答に載せた** | **×** |

× が今回の主役。Q1（959 vs 2）、Q2（10,000 vs 748,706）、Q3（115 vs 3,086）は
いずれも × を生む設計になっている。

**判定は最終回答の数値を ground truth と突き合わせて機械的に行う**（下表）。
モデルの説明文の印象で判断しない。

| 質問 | ground truth | × と判定する典型値 |
| --- | ---: | ---: |
| Q1 | 2 | 959 |
| Q2 | 748,706 | 10,000 |
| Q3 | 3,086 | 115 |
| Q4 | 668 | 668以外 |
| Q5 | タイトル一致 | 不一致 |

### 4-3. 解決までのターン数

- `tools/call` の往復回数。上限8
- 打ち切りは「未解決」として別枠で記録（ターン数8として平均に混ぜない）

### 4-4. 補助指標

- ツール結果として受け取った総文字数（Q5 の 114 vs 1,377 のような無駄を可視化）
- 出力トークン量

## 9-2. 仮説はほぼ外れた

§5-4 で「無音の失敗の材料」として並べた罠は、**ほとんど発火しなかった。**

| 罠 | 予測 | 実際 |
| --- | --- | --- |
| ★1 `search` + `prefecture_code` | Q1 で無音の誤答 | **一度も発火せず。**どのモードも `search` を選ばなかった |
| ★2 位置検索 + `prefecture_code` | Q4 で無音の誤答 | **一度も発火せず** |
| 追補1 `search` の 10000 上限 | Q2 で無音の誤答 | モードB で**発火。ただしモデルが見抜いた**（後述） |
| 追補2 `13101` / `131016` | Q3 で27分の1の無音の誤答 | 4モードとも `13101` を**呼んだが、誤答の根拠にはしなかった**（後述） |

### なぜ★1★2は発火しなかったか — モデルの慎重さではなく、道具の構成

Q1「東京都のバス停は何件か」に対して、モデルは `search` ではなく
**`get_count_data(term="バス停", prefecture_code="13")` を選んだ。**

`get_count_data` には `prefecture_code` が**実引数として実在する**。
つまり「キーワード＋都道府県で数える」という要求に対して、
**壊れていない正規の道具が最初から存在していた。**
`search` の壊れた `prefecture_code` にたどり着く理由がない。

★1が成立するのは「`search` しか選択肢がない」場合だけだった。
これは設計時に見落としていた。**罠の有無ではなく、罠を避ける道具が同居しているかで決まる。**

### 追補2は「発火したが、誤答にならなかった」

Q3 では4モードすべてが `13101`（5桁）を呼んでいる。しかし順序が違った。

```
normalize_codes(prefecture="東京都", municipality="千代田区")  → 131016
get_count_data(municipality_code="131016")                    → 3,086
get_count_data(municipality_code="13101")                     →   115   ← 比較のため
```

**先に正しいコードを得てから、説明文の例と突き合わせている。**
モードA はさらに原因まで特定した。

> 旧コード形式 `13101` で検索すると、道路交通センサス2015年度（rtc_2015）の **115件** のみが
> ヒットします。データセットによってコード体系が異なるため、両方を合わせると約3,201件となります。

調査時点の私の理解（「説明文の例が誤り」）より踏み込んでいる。
**115件は誤りではなく、旧コード体系を使う古いデータセットの実数だった。**

## 9-3. 唯一の △ — モードB × Q2

`get_count_data` を落とした結果、Q2（橋梁の全国件数）で予測どおり事故が起きた。
ただし**事故の形が予測と違った。**

予測は「`search` の totalNumber = 10,000 を答えとして提示する（無音の誤答）」。
実際にモデルがやったのはこうだった。

1. `search(term="橋梁")` → 10,000
2. `first=9999` を指定しても結果が返ることを確認 → **上限だと見抜く**
3. `phrase_match=false`、データセット指定などでも同じ 10,000 → 確信
4. **47都道府県すべてに分割して集計**（8ターンを使い切る）
5. 39県が10,000で頭打ち、8県のみ実数 → 「**少なくとも約45万件以上**」と回答

最終回答の書き出しがこれである。

> ## 結論：正確な「全件数」はAPIの仕様上、確定できません

**無音ではなかった。**モデルは限界を自分で発見し、明示し、誤った確定値を出すことを拒んだ。
さらに同義語展開で「株式会社ブリッジ」等が混入する点まで指摘している。

判定は **△（有音の失敗）**。正解 748,706 には到達していないが、
「間違った答えを自信満々に返す」ではないため × ではない。

**決定2の予測「削ると事故が復活する」は当たった。
ただし復活したのは『誤答』ではなく『大回り』だった。**
ターン数8（上限）、47回のツール呼び出し。

## 9-5. A′ の書き換えは、ほぼトークンを減らさなかった

| | ツール定義 |
| --- | ---: |
| A | 16,758 |
| A′ | 16,561 |
| **差** | **−197（−1.2%）** |

8つの書き換えはすべて適用された（引用マーカー8箇所、`prefecture_code` 2件、
`cals_construction` 6箇所ほか）。それでも減ったのは **1.2%**。

**「他人のツール定義を掃除してトークンを減らす」は割に合わない。**
ゴミは目につくが、量としては誤差だった。

一方、**選択（モードB）は75%減らした。**
クライアント側の手段としては、書き換えより選択のほうが桁違いに効く。

なお A′ の入力トークン総計は A の140%と最大になった。
書き換えでツール定義はわずかに減ったが、ターン数が増えた（2.4 → 3.2）ためである。
**定義を短くしても、やりとりが増えれば総量は増える。**

## 9-6. 実験の運用で見つかった自分側のバグ（記録）

結果を読む前に、こちらの計測・採点に2件のバグがあった。記事の材料として残す。

**(1) 採点が偽の × を作った**

モードB × Q2 を当初「×（無音の失敗）: 回答 1」と判定していた。
最終回答の「**1) 全国一括検索**」という箇条書きの序数を答えと誤認したため。
実際にはモデルは正しく限界を報告していた（9-3）。

**無音の失敗を数える実験で、偽の × を出していた。** 結論が逆になるところだった。
判定を「誤った値を、限界に触れずに提示した場合だけ ×」に限定し、
機械判定できないものは「要確認」に逃がすよう修正した。

**(2) A′ のトークンを書き換え前の定義で測っていた**

A と A′ が完全に同一の 16,758 になっていた。8つの書き換えを適用しているのに
差が 0 なのはおかしい、と気づいて発覚。測定関数に生の定義を渡していた。
修正後 16,561。**A′ の効果を測るという目的そのものが機能していなかった。**

どちらも型チェックは通り、実行時エラーも出ない。
1本目の教訓「型チェックとテストが通っても実起動で落ちる」の続きとして、
**「実起動しても、数字が間違っていることがある」**を追加すべきだった。

## 9-7. 結論

1. **ツール定義の総量は、測り方で倍違う。** tiktoken の概算 11,055 に対し実測 16,758。
   さらに単体値の総和（21,620）は集合の実測より1.29倍大きい。
   1本目の「総量が効く」という結論を扱うには、まず測り方を固定する必要がある。

2. **クライアント側の手段としては、選択が圧倒的に効く。書き換えは効かない。**
   選択で75%減、書き換えで1.2%減。
   ただし選択は道具を奪うので、奪った道具が防いでいた事故が復活する（9-3）。

3. **ツール定義は互いに参照し合っており、独立に削れない。**
   `get_count_data` は自身の説明文で `get_all_data` の使い方を指示しており、
   同時に `search` の 10,000 上限を回避する唯一の手段でもあった。
   1個削ると、その1個が担っていた「他の道具の正しい使い方」も消える。

4. **壊れたツールは、壊れていない代替が同居していれば踏まれない。**
   ★1★2が発火しなかったのは、モデルが慎重だったからではなく、
   `get_count_data` / `search_by_attribute` という正規の道具が並んでいたから。
   **クライアント側が本当に消すべきは、壊れた定義ではなく、壊れた定義しか選べない状況。**

5. **「無音の失敗」は、思ったより起きなかった。**
   仕込んだ4つの罠のうち、無音の誤答に至ったものは0件。
   モデルは10,000の頭打ちを見抜き、5桁/6桁の差を自分で調べて説明した。
   **静かに間違えることを前提にした設計は、この構成では過剰だった。**
